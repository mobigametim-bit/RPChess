# B9 — аудит генератора карты и план миграции

Дата аудита: 7 августа 2026.

Источник требований: Notion «11 — Roadmap, планирование и журнал решений», решения №15–50, а также «05 — Кампания, узлы, события и режимы».

## Итог

Текущий Stage B runtime содержит полезную переходную реализацию карты, но не соответствует production-контракту B9. Основные расхождения: единственный процедурный каркас вместо шести макрошаблонов; заранее назначенное содержимое всех узлов; квоты на событие, сервис и элиту; стоимость перехода 1–2 припаса; встроенный тайный узел вместо независимой проверки; отсутствие versioned generator state, резервной карты, форсированного марша и сохранённой материализации уровня.

Новые правила реализуются отдельным генератором версии 3. Старые сохранения не регенерируются: их существующий граф и уже назначенное содержимое переводятся в материализованное legacy-состояние.

## Жёстко встроенные конфликтующие правила

- `stageBTypeFor` задаёт типы по номерам слоёв и гарантирует конкретные категории.
- `forceMandatoryNodeTypes` принудительно создаёт event, service и elite.
- `assignContent` материализует все contentId при старте акта.
- `enrichStageBNodes` заранее создаёт intel для всей карты.
- `connectLayers` назначает стоимость 1–2 припаса.
- `createCampaignState` гарантирует запас припасов относительно минимального пути.
- `travelTo` запрещает движение при нуле вместо форсированного марша.
- secret-node является обычным узлом графа и может раскрываться через scouting.
- `validateActGraph` требует хотя бы одно событие и хотя бы один сервис, что является запрещённой квотой.

## План миграции

1. Ввести production generator v3 и шесть макрошаблонов без замены legacy API.
2. Генерировать при старте только топологию, тип, фазу, опасность, профиль ветви и derived seed.
3. Добавить `materializedContentByNode` и одновременную материализацию всех соседей при открытии уровня.
4. Добавить campaign schema 3: revealed levels, закрытые/reopened ветви, completed/rewarded nodes, forced march и secret state.
5. Мигрировать schema 1–2 без повторного запуска генератора: существующие `contentId` считать уже материализованными.
6. Подключить scenario selector и event selector через общие callbacks. PR №58 после слияния B9 должен использовать этот контракт вместо собственного хранения содержимого узла.
7. Перевести browser host и vertical-slice runtime на schema 3 после прохождения unit/statistical/reload tests.
8. Удалить старые квоты и stageBTypeFor только после browser acceptance и проверки legacy saves.

## Минимально изменяющее архитектуру решение

Production generator добавляется рядом с legacy-генератором, затем подключается адаптером. Это сохраняет старые replay/save snapshots и не заставляет PR №58 дублировать карту. Единственным источником истины для выбранного события остаётся материализованное содержимое узла; selector PR №58 возвращает assignment и обновлённое selector state через callback.
