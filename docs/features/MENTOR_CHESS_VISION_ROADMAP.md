## 1. Продуктовые решения — утверждено

1. **B / Два шага обучения.** После того как ученик самостоятельно находит угрозу, **предложить** второе необязательное упражнение — вернуться к позиции *перед* ошибкой и попробовать более сильный собственный ход. Не принуждать, сохранить возможность сразу продолжить партию.
2. **B / Объяснение после ответа.** До выбора игроком — вопрос, подсказки по запросу и проверяемая реакция на доске; **не раскрывать** конкретную причину/ход текстом LLM. После самостоятельного ответа (или явного «Показать ответ») показать верифицированный разбор и при необходимости связный комментарий LLM. Модель не подменяет шахматный источник истины.
3. **B / Позиционные ошибки — без остановки.** Если оценка ухудшилась, **но не подтверждена конкретная непосредственная тактическая угроза**, не останавливать ответ соперника, не предлагать нажать на произвольную фигуру, показывать **короткий проверенный комментарий**. Не превращать ход из первой PV в искусственную «угрозу», если факт/причина не подтверждены. Это правило имеет приоритет над текущим поведением PR #187, которое останавливает все неточности/ошибки/зевки.
4. **B / Адаптивная производительность.** Быстрая оценка — по умолчанию, углублённый анализ — только для подтверждения/разрешения неоднозначных ситуаций; лимит времени и безопасный отказ на медленных телефонах. Не держать партию бессрочно в ожидании Stockfish или Gonka.

**Вне объёма:** бывший этап 7 — персональный профиль навыков, накопление истории ошибок, интервальное повторение и генерация личной библиотеки задач. Не разрабатывать и не закладывать новую систему хранения ради этого. Окончательная дорожная карта состоит из **7 этапов**: прежние 1–6 и завершающий этап тестирования/выпуска (бывший № 8).

## 2. Контракт UX (целевое состояние)

### Подтверждённая непосредственная тактическая угроза

1. Игрок делает ход. Быстрый Stockfish вычисляет оценку до и после; при необходимости запускается ограниченная уточняющая проверка. Пока идёт проверка, нельзя запускать два конкурентных хода соперника.
2. При **подтверждённой** тактической угрозе соперник не отвечает. На *настоящей позиции после хода игрока* автоматически появляется вопрос, какой фигурой соперник может реализовать угрозу. Угрозу и выбираемую фигуру определяет шахматный анализатор; первый ход единственной PV сам по себе не считается достаточным доказательством.
3. Неправильная фигура — красная мигающая аура и крупная красная фраза, вылетающая из выбранной фигуры. Правильная — зелёная аура и зелёная фраза. В панели наставника **не дублировать** эти реплики, не повторять подсказки и вопрос после правильного ответа. Подсказки 1/2 — только по запросу, до ответа.
4. После правильного ответа или явного раскрытия решения показать конкретный проверенный ход, атакованные клетки, суть мотива и короткое полезное правило. Лишь **после** этого разрешается развёрнутый комментарий LLM. Если Gonka недоступна, детерминированный разбор остаётся.
5. Предложить выбор: **«Исправить ход»** (необязательное второе упражнение) или **«Продолжить партию»**. Исправление сначала проводится во **временной учебной вариации**, не меняющей настоящую историю, курсор, награды или результаты. Stockfish оценивает альтернативу по качеству позиции (допускает равнозначные варианты), а не по совпадению с одной UCI-строкой. Завершение вариации возвращает к исходной партии; продление/замена реального хода без явного отдельного действия запрещены.
6. «Продолжить партию» разблокирует прежний ChessAIAdapter, после чего соперник действительно делает свой ход по текущему Elo. Его ход может отличаться от изученной PV — это нормально.
7. Пропуск, ошибка сети, отмена и перезагрузка не запирают пользователя. Состояние паузы/временной вариации безопасно восстанавливается либо отменяется без незаметного ответа соперника.

### Неточность/ошибка без доказанной непосредственной тактики

- Не блокировать ответ соперника. Отображать короткую формулировку об ухудшении позиции **без выдуманного мотива**, желательно с проверенным фактом, если он есть.
- Не задавать вопрос «какой фигурой соперник ответит?» только потому, что Stockfish нашёл легальный первый ход. Не выдавать события на 3–10-м полуходе за немедленную угрозу.
- Не запускать платную развёрнутую LLM-цепочку только ради короткого комментария; достаточно безопасной локальной формулировки. Это снижает задержки/затраты.
- Удачные ходы и обычное течение партии сохраняют текущее поведение.

**Промежуточный результат этапа 2 (2026-11-07):**
- Реализованы чистые функции \`mentorCpWinProbability\`, \`mentorScoreWinProbability\`, \`trainingMoveQualityWinChance\` в \`game/js/mentor-training-history.mjs\`. - В текущем Mentor API Worker (\`rpchess-mentor-api-preview\`) запрос проверяется \`trainingMoveQuality\` по **старым** порогам 65/120/250 cp. Поэтому новый классификатор **пока не подключён** к реальной игровой оценке и запросам ИИ: клиентская смена без серверной приведёт к HTTP 422 \`invalid_grade\`. Синхронное переключение клиента, валидатора Worker и обновление тестового API будет этапом 6; \`main\` и боевой API не менять без разрешения.
- Существующий \`tests/mentor-training.cjs\` дополнен проверкой распределения категорий на разных уровнях преимущества, отсутствия ложного зевка уже выигранной позиции, оценки лучшего хода, отказа при малой глубине, создания и потери форсированного мата, а также совместимости UCI-счёта.
- Исторические метки партий Lichess из эталонного корпуса нельзя считать обязательными ожидаемыми категориями нашей сборки: глубина, версии движков, статистическая модель и дата анализа отличаются. Они служат ориентирами для обсуждения спорных примеров, а не непреложным арбитром.

**Осталось для полного закрытия этапа 2:** параллельно с этапом 6 обеспечить согласованный протокол классификации \`v2\` на статическом preview и отдельном Mentor API Worker; затем проверить классификацию и тексты на эталонах, прежде чем объявлять новый алгоритм активным.

### Этап 4 — Мотивы, MultiPV и подтверждение непосредственной угрозы

**Изменения:**
- Сохранить 18 текущих категорий, но добавить каждому событию источник и степень доказанности: легальный наблюдаемый мотив, выгодное взятие (SEE), реальное ухудшение оценки, ответ на лучшую защиту.
- Расширить поддержку сложных мотивов (отвлечение, завлечение, промежуточный ход, жертва, ловушка, матовая сеть) **только при программной проверке**, без объявления ложных «форсированных выигрышей».
- Использовать существующий `StockfishReviewEngine` и MultiPV=2 для первичного сопоставления; при спорных случаях — ограниченный дополнительный анализ. Не путать длину PV до 20 полуходов с глубиной поиска.
- Добавить явный результат классификации: `verified_immediate_tactic` либо `unverified_or_positional`. **Только первый** разрешает остановить соперника и задать вопрос; второй запускает короткий комментарий и обычный ответ соперника.
- Разнести сигналы «первый законный ответ» и «проверенная причина потери оценки». Не считать любой первый ход Stockfish достаточной тактической уликой.

**Приёмка:** упражнения запускаются только на подтверждённой угрозе; неоднозначная или позиционная ошибка не блокирует соперника; реальная защита может опровергнуть слабую «комбинацию».

**Реализация этапа 4 (2026-11-07):**
- \`game/js/mentor-training-threat.mjs\` теперь отдельно проверяет **действительно немедленную** тактику в *позиции после хода игрока*. Быстрый \`StockfishReviewEngine\` (260 мс) выявляет только кандидата; если кандидат отсутствует, глубокого поиска **нет**, соперник сразу отвечает и локально появляется короткий комментарий о том, что непосредственная угроза не доказана.
- Только для кандидатов углубляем анализ до 1700 мс. Для подтверждения нужны согласованные первые ответы быстрого и глубокого Stockfish, глубина fast≥5/deep≥7, близость оценок (≤280 cp) и независимый программный факт: **мат в один ход**, выгодное легальное взятие с полным SEE (≥100 cp), реальное превращение, проверенная вилка с шахом королю и атакой на ладью/ферзя без немедленного взятия атакующей фигуры, реальный двойной или вскрытый шах. Геометрия событий следующих полуходов PV не достаточна.
- Если MultiPV показывает **практически равноценный ход другой фигурой** (разрыв ≤65 cp при сопоставимой глубине), вопрос с единственным правильным выбором не задаётся. Альтернативный ход и оценка сохраняются в диагностических данных. **Ограничение:** MultiPV-2 представляет альтернативы **соперника**, а не исчерпывающий анализ **защит игрока** после угрозы; доказательство форсированности всей комбинации не заявляется. Распознавание всех 18 категорий остаётся в \`tacticalEvidence\`, но не все категории пока могут безопасно разрешить остановку.
- При подтверждении \`verified_immediate_tactic\` автоматически активируется прежнее упражнение прямо на текущей доске, сохраняется пауза и после явно выбранного продолжения отвечает настоящий соперник. При \`unverified_or_positional\` — **без паузы, без отдельного вопроса, без LLM-запроса, без кнопки учебного отката**, только краткий RU/EN комментарий. Ошибка проверки/таймаут не оставляет вечной паузы. Позиционная ошибка остаётся отмеченной в истории, но не притворяется доказанной тактикой.
- Совместимый протокол \`mentor-api-preview\` и старые пороги оценок в сантипешках **пока сохранены**, новый выигрышно-вероятностный классификатор этапа 2 ещё не активирован. Интерфейс, серверный текст LLM и отдельный API Worker здесь не деплоятся.
- Существующие \`tests/mentor-training-feedback.cjs\` и \`tests/mentor-training-browser.cjs\` расширены: мат в один, положительный и нулевой SEE, невыгодное взятие ферзём, геометрически выглядящий мотив без доказанного выигрыша, тихий ход, разногласие глубины/первого хода/оценки, MultiPV с двумя ответами разными фигурами; браузерная проверка подтверждает, что позиционная ошибка не блокирует соперника, не тратит 1700 мс на доп. поиск и не вызывает платный API. Новые постоянные тестовые наборы не создавались.
- **Ограничения для ручной приёмки:** консервативный фильтр может сознательно пропускать нестабильную тактику, допустимы ложноотрицательные срабатывания. Профили в которых реальная жертва/компенсация и сложная вилка доказаны только несколькими ответами, должны быть расширены позже при наличии отдельного проверяющего алгоритма. Не выдавать текущий фильтр за всеобъемлющую реализацию стратегического анализа.

### Этап 5 — Два учебных задания в одном UX

**Изменения:**
- В `game/js/mentor-training-app.mjs` и `mentor-training-teaching.mjs` реализовать автоматический вопрос на текущей позиции, двухступенчатые подсказки, красный/зелёный визуальный отклик; не раскрывать решение до самостоятельного выбора.
- После правильного ответа скрывать вопрос, все подсказки и реплику «Верно…» из панели; показывать краткий достоверный разбор.
- Предложить «Исправить ход» / «Продолжить партию»; в тренировочной ветке из FEN *перед* ошибкой разрешить альтернативный ход, сравнить его оценку с лучшим, принять несколько достаточно хороших ходов.
- Сохранить настоящую историю, местоположение на доске и стабильное возобновление игры; не допускать двойного хода соперника и потери восстановленной сессии.

**Приёмка:** на телефоне проходит путь «ошибка → поиск угрозы → объяснение → необязательное исправление → продолжение»; другие ошибки идут без паузы, английский язык и портрет/ландшафт работают.

**Реализация этапа 5 (2026-11-07):**
- После правильного обнаружения тактики (или явного «Показать ответ») панель предлагает два выбора: **«Исправить ход»** и **«Продолжить партию»**. Исправление полностью **необязательно**: пользователь может сразу отпустить соперника. До решения угрозы кнопка исправления не показывается.
- Кнопка «Исправить ход» открывает **отдельную учебную позицию FEN *до* ошибки** и предлагает сделать свой альтернативный ход непосредственно на доске (клик, перетаскивание, выбор фигуры превращения). `correctionView` — временный объект, существующий отдельно от `moves`/`cursor`/`pausedEntry`. **Реальная партия, её история и результат не меняются ни при удачном, ни при неудачном учебном ходе**.
- Для оценки повторно использован существующий `gradeReviewAttempt` из `finished-game-review.mjs`: сначала проверяется законность; лучший вариант Stockfish принимается без лишнего поиска; другие варианты оцениваются повторно по позиции **после** альтернативного хода, а не по совпадению строки UCI. Допуск **70 сантипешек** (порог действующего законченного Game Review). Недостаточная глубина/ошибка анализа — нейтральное «не удалось проверить», а не ложный успех или провал.
- После хорошего варианта отображается позитивное объяснение, предлагаются «Другой вариант», «К объяснению», «Продолжить партию». После плохого варианта — предложение повторить попытку без раскрытия готового хода. Проверки не вызывают LLM, и соперник отвечает только после явного «Продолжить партию».
- UI и сообщения локализованы RU/EN и адаптированы под телефон. При обновлении страницы в середине исправления исходная партия остаётся на паузе, а уже решённый вопрос об угрозе **не приходится проходить повторно**: сохраняется флаг `lessonSolved`, восстанавливается просмотр подтверждённого ответа. Неполная пробная позиция сознательно не сохраняется в историю.
- Используются существующие тесты: в `tests/mentor-training-feedback.cjs` проверены допустимая альтернатива, сам зевок, лучший ход, незаконный ход и недостаточная глубина; `tests/mentor-training-browser.cjs` проверяет полный путь исправления, стабильность FEN и истории, возврат к объяснению, reload и ответ соперника только после завершения упражнения.
- **Граница этапа:** это пока оценка в пределах стандартных 260 мс и фиксированный допуск в 70 cp. На этапе 7 можно повысить точность для пограничных альтернатив адаптивной повторной проверкой. Новый выигрышно-вероятностный классификатор этапа 2 не включён в существующий Mentor API, серверный педагогический промпт не менялся; это задачи этапа 6.

### Этап 6 — Серверный LLM как педагогический редактор, не шахматный судья

**Изменения:**
- В `game/js/mentor-training-feedback-core.mjs` передавать модели задачу на объяснение подтверждённого факта и учебного принципа, не перекладывать на неё самостоятельный анализ FEN/PV.
- Подготовить структурированные `fact IDs` и проверяемые данные (фигуры, клетки, угроза, выгодность размена, альтернативные защиты, шаг урока, результат ответа игрока). Координаты можно возвращать **только** как ссылки на факты, уже проверенные программно.
- Показ развёрнутого текста — после ответа или явного раскрытия решения. До этого LLM не должна выдавать спойлеры; возможна быстрая локальная реакция без ожидания сети.
- Обновить проверку текста, таймауты/повторы и стоимость обращений. Сохранить безопасный fallback и отсутствие платного вызова для обычных позиционных неточностей.
- Сначала отдельная тестовая версия API Worker с разрешённым origin и небиллирующими CORS-проверками; боевой API не перезаписывать.

**Приёмка:** валидные человеческие объяснения на эталонах без выдуманных ходов/клеток/разменов, спойлеров до ответа, ложных выводов о форсированности; подтверждённые ответы гонки не меняют шахматное состояние партии.

**Промежуточный результат этапа 6 (2026-11-07):**
- Новая **отдельная схема v2**, не совместимая со старым валидационным протоколом \`/v1/explain\`: \`game/js/mentor-training-feedback-v2.mjs\` выполняет повторную проверку законности FEN/ходов, сверяет диагноз по **изменению шансов победы** и повторно вызывает \`verifyImmediateThreat\` по быстрому и углублённому Stockfish. Проверяются конкретный первый ответ, тип мотива, его доказательная основа, SEE/MultiPV. Подставленная клиентом «вилка» без доказательств отклоняется **до** вызова LLM.
- Теперь **вычислительный классификатор из этапа 2 активирован на клиенте**; в v2 API категория вычисляется заново той же чистой функцией \`trainingMoveQualityWinChance\` (порог 10/20/30 процентных пунктов). Старый /v1, его парсер и действующий Worker **не переписывали и не деплоили**. Это ещё не доказывает калибровку вероятности на широком историческом массиве — остаётся для этапа 7.
- Модель получает **только** проверенную словесную угрозу, \`factId\`, учебный принцип и вопрос; **не получает** FEN, PV, лучший ход ученика, координаты или оценочные числа. Ожидается JSON \`{"advice":"..."}\`: 1–2 предложения об общей привычке проверки позиции, без новых шахматных утверждений. \`verifiedFact\` генерируется локальным проверяющим алгоритмом и **добавляется к совету моделью/сервером лишь после валидации**. Запрещены выдуманные ходы, клетки, фигуры, взятия и конкретные тактические заявления; такой текст отклоняется, после чего доступен безопасный локальный fallback. Свободный естественный язык всё ещё ограниченно проверяем, поэтому достоверные конкретные факты остаются полностью детерминированными.
- В клиенте \`game/js/mentor-training-app.mjs\` **больше нет платного запроса до ответа**: LLM вызывается **после** выбора верной фигуры либо явного «Показать ответ». ИИ не открывает решение заранее. В UI после решения показывается проверенный разбор, а затем общий педагогический совет; повторная попытка вручную остаётся, при reload зависший запрос не перезапускается с новым списанием автоматически.
- \`mentor-api/src/v2-index.mjs\` и \`mentor-api/wrangler-v2.toml\`: **новый** Cloudflare Worker \`rpchess-mentor-api-v2-preview\` c собственными ограничениями запросов, без доступа к данным и без затрагивания \`rpchess-mentor-api-preview\`. Отдельная сборка \`.github/workflows/mentor-thinking-evidence-preview.yml\` деплоит только v2 по точной конфигурации, проверяет CORS/health/невозможность вызова v1 и не делает платных тестовых вызовов Gonka.
- **Конфигурация сервера:** первый деплой нового Worker сообщил \`configured:false\`: соответствующий \`GONKA_API_KEY\` **не доступен как секрет GitHub Actions**, и Cloudflare изолирует секреты между Workers. Отсутствие ключа не блокирует игру: клиент возвращает программный \`verifiedFact\` и локальную подсказку. Чтобы реально использовать DeepSeek v2, требуется добавить **GitHub Actions Secret** \`GONKA_API_KEY\` (Settings → Secrets and variables → Actions) или отдельно \`wrangler secret put GONKA_API_KEY --config mentor-api/wrangler-v2.toml\`, используя свои полномочия; значения в коде, логах и чате не публикуются.
- Тесты расширены **без нового suite**: в \`tests/mentor-training-feedback.cjs\` есть подделка мотива, неправильная категория, попытки выдумать конкретные ходы и клетки, CORS, отказ в плохом запросе до платного fetch, согласованный ответ клиент/сервер; в Chromium проверено, что запрос **не стартует до самостоятельного ответа**, и что retry не меняет партию. Эти тесты использовали **мок ответа модели**, а не подтверждение качества реального Gonka.

**Остаётся до полной приёмки этапа 6:** проверить health \`contractVersion:2\` и v2 API CORS на живом домене после исправления порядка валидации, безопасно установить серверный секрет (только после готовности пользователя) и провести один ограниченный реальный тест DeepSeek + проверку ответа. Боевой API и \`main\` без изменений.

Статическая сборка: https://rpchess-mentor-training-preview.mobigametim.workers.dev/?mentor_ui=20261107-v4. **Ничего не сливать в `main` без явного подтверждения пользователя**. VK и прежний Mentor API v1 не тронуты.

### Уточнение UX исправления хода — 2026-11-07

- При неудачном исправлении прежнее красное сообщение «Этот ход недостаточно улучшает позицию. Попробуй другое продолжение.» **не дублируется в панели**: оно возникает красной анимированной репликой от исходной фигуры на учебной доске. Исходная партия и учебная позиция остаются без изменений; игрок может попробовать другой ход. Красная реплика живёт 3,6 секунды, чтобы длинную фразу можно было прочитать. RU/EN.
- На учебной доске исправления добавлена кнопка **«Сильный ход» / Strong move**. Она сначала заблокирована и отображает обратный отсчёт с 10 до 1; разблокируется только после фактического истечения 10 секунд. Кнопка показывает проверенный лучший UCI-ход Stockfish **из позиции до ошибки**: учебная фигура перемещается, клетки начала/конца подсвечиваются, координаты показываются в панели. Реальная история партии, сохранение и ответ соперника не изменяются; «Другой вариант» возвращает учебную позицию. Новых LLM/API вызовов нет.
- Таймер обновляет только содержимое кнопки, не перерисовывает доску и не сбрасывает анимации. При выходе из учебного упражнения старый отсчёт прекращает влиять на новый экран; повторное открытие запускает новый отсчёт.
- Изменения проверяются существующими Chromium-регрессиями: блокировка до истечения времени, правильное включение и показ Stockfish, неподвижность оригинальной партии, красная реплика из фигуры и направление анимации для крайних горизонталей. Ветки `main`, боевой VK и Mentor API v1 остаются без изменений. Требуется ручная приёмка в тестовой сборке.
