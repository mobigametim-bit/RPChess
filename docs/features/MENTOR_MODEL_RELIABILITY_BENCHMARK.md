# Gonka: контролируемый тест стабильности наставника

Дата: 2026-11-07. PR #186, не main.

## Цель
Сравнить реальный ответ трёх моделей на одну и ту же проверенную шахматную позицию (1.f3 e5 2.g4??, немедленный мат). Все модели получают идентичные system/user prompts, FEN, Stockfish PV и факты тактики.

## Метрики
* Число запросов на модель и на конфигурацию.
* Процент полученных и принятых программной проверкой ответов.
* p50/p95 времени ожидания и средняя задержка.
* Частота сетевой ошибки, HTTP 429/5xx, таймаута, пустого текста, невалидного JSON, невалидной длины и 2–5 предложений.
* Токены из поля usage, если провайдер его возвращает.
* Дословный пример успешного ответа каждой модели на одну позицию.

## Серии (максимум 600 по разрешению пользователя)
Начальный сопоставимый эксперимент: **72 вызова** = 8 повторений × 3 модели × 3 конфигурации:
- baseline: текущая json_object схема и настройки, без явного выключения reasoning.
- fast: json_object и reasoning_effort: none, где модель поддерживает.
- schema: строгий json_schema для DeepSeek и MiniMax, JSON mode для GLM, reasoning_effort: none где поддерживается.

Серии выполняются последовательно с межзапросным интервалом не меньше 4,1 с, с не более чем одним внешним запросом модели на измерение. Бюджет ответов 900 токенов. Замена модели внутри измерения ЗАПРЕЩЕНА. Таймаут DeepSeek 15 с, MiniMax/GLM 10 с, как в публичном режиме. Сумма внешних запросов не должна превышать 600. Код теста: mentor-benchmark/run.mjs.

## Безопасность
Временный случайный 256-битный токен генерируется в GitHub Actions, помещается только в Cloudflare secret и во временный локальный файл runner, не публикуется. Эндпоинт /_internal/benchmark без этого секрета возвращает 404; дополнительные ограничения через Cloudflare rate limiter. Токен удаляется после тестирования командой wrangler secret delete. Логи содержат только статистику и ответы на публичную синтетическую шахматную позицию; ключ Gonka, bearer и имена других секретов не выводятся.

После результата выбираем наиболее устойчивую конфигурацию и повторяем контрольное тестирование в рамках неизрасходованного бюджета. Если исходные модели нестабильны из-за внешнего сервиса, не утверждаем гарантированной надёжности — сохраняем failover и заглушку.

Контрольная серия № 2: 60 вызовов (20 × 3 модели), конфигурация optimized: DeepSeek — json_schema + reasoning_effort none, 15 секунд; MiniMax — json_object, 18 секунд; GLM — json_object + reasoning_effort none, 20 секунд. На старте проверяем готовность временного токена без платных обращений, чтобы не считать задержку развертывания ошибкой модели.

Третья серия: 30 вызовов только MiniMax M2.7 с json_object, max_tokens 900 и увеличенным таймаутом 18 секунд. Цель: проверить, исчезают ли `finish_reason=length` и `invalid_json`, обнаруженные при 1200 токенах.

## Итог трёх диагностических серий

Все измерения проведены на одинаковом легальном запросе после 1.f3 e5 2.g4??. Число прямых вызовов моделей: **72 + 60 + 30 = 162**, повторов из-за rate limit — 0. Серии не заменяют качественной шахматной экспертизы ответа.

| Модель / формат | Попытки | Успех | Медиана | Отказы |
|---|---:|---:|---:|---|
| DeepSeek, baseline JSON | 8 | 6 | 3313 мс | 1 таймаут, 1 временный 404 на доступе к тестовому endpoint |
| DeepSeek, JSON Schema + no reasoning + 1000 tokens + 15 с | 20 | **19 (95%)** | **477 мс** | 1 таймаут |
| MiniMax, baseline JSON + 900 tokens + 10 с | 8 | 6 (75%) | 451 мс | 2 таймаута |
| MiniMax, JSON + 1200 tokens + 18 с | 20 | 2 (10%) | 441 мс | 18 JSON errors, все с finish_reason=length и completion_tokens=1200 |
| MiniMax, JSON + 900 tokens + 18 с | 30 | **27 (90%)** | **653 мс** | 3 JSON errors, все с finish_reason=length и completion_tokens=900 |
| GLM, baseline JSON + 10 с | 8 | 0 | 10000 мс | 8 таймаутов |
| GLM, JSON + no reasoning + 1200 tokens + 20 с | 20 | **17 (85%)** | **698 мс** | 3 таймаута |

**Выбранные настройки:**
1. DeepSeek: strict json_schema, reasoning_effort=none, max_tokens=1000, timeout 15 с.
2. MiniMax: json_object, без попыток отключить недоступное thinking, max_tokens=900, timeout 18 с.
3. GLM: json_object, reasoning_effort=none, max_tokens=1200, timeout 20 с.

Результаты MiniMax подтверждают, что произвольное повышение max_tokens может ухудшать стабильность в конкретной реализации Gonka. HTTP 200 с незавершённым JSON не считается успешным ответом. Прямой запрос относится только к одной модели, не к цепочке fallback.

**Ограничение эксперимента:** одна и та же позиция может попадать в кэш брокера, а сбои трёх моделей на одной платформе могут быть коррелированы. Нельзя экстраполировать эти проценты на все позиции или гарантировать 100% ответ. Отдельный end-to-end smoke проверяет игровую цепочку через /v1/explain, а не тестовый endpoint.
