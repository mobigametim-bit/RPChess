# Турнир / PvP 10+0 — журнал реализации

Статус: **рабочий staging с настоящим матчем двух игроков**, feature/tournament-pvp-mvp-20261022, draft PR #164. В main не переносить до приёмки экономики и безопасности.

## Продуктовые решения
- Классика 10+0: по 10 минут каждому без инкремента.
- Подбор от Мощи Путешествия; PvP должен менять общую Мощь после подтверждённого результата.
- ВК и прямые игроки GitHub Pages в одной PvP-системе.
- Купленные на Арене расы — косметика; Люди по умолчанию.
- Приглашение по ссылке/коду, случайный поиск; предложение сыграть с ботом только с явным обозначением ИИ.
- PvP-награды в Осколках чести только через сервер, без клиентских самоотчётов.

## Турнир: шах и связки — визуальные эффекты (23.10.2026)

- Турнир использует ту же красную ауру шаха `assets/vfx/aura_red.png`, что и Арена. Класс `classic-square--check` ставится королю стороны под шахом из авторитетного шахматного snapshot; ориентация доски игрока на определение клетки не влияет.
- Турнир использует общий `applyPinIce` из `game/js/king-pin-ice.mjs` (без собственной копии правил). Полная абсолютная связка: `pin_ice_full.png`, частичная: `pin_ice_partial.png`. Прозрачность 50%, анимация появления 160 мс и `prefers-reduced-motion` уже реализованы в общем модуле.
- Серверные polling snapshots каждые 2,4 секунды больше не пересоздают доску и ледяные слои, если FEN и выбранная клетка не изменились. При изменении позиции после хода эффекты пересчитываются на обоих клиентах.
- Расширен существующий двухбраузерный live PvP E2E: последовательность Рюи Лопес (2...Nc6 3.Bb5 d6 4.Bxc6+) проверяет полную связку на c6, красную ауру короля e8 после шаха, удаление ледяной накладки после взятия и стабильность слоя между опросами. Частичная связка дополнительно покрыта существующими тестами общего `king-pin-ice`.
- Только ветка PR #164, без слияния в `main`; ручная приёмка ещё обязательна.

## НЕ готово, нельзя заявлять о релизе
1. Подлинная VK-идентичность: до установки отдельного `VK_APP_SECRET` подключение VK работает как гостевое. Профиль прямого GitHub Pages также гостевой и зависит от токена устройства.
2. Защищённое изменение Мощи Путешествия и Осколков чести после PvP, дедупликация server receipts, антифарм, защита от накрутки матчами друзей. Пока награды и Мощь **не начисляются**.
3. После двух проигрышей подряд подбор должен делать сервер (сейчас интерфейс передаёт нулевую серию, а сервер допускает клиентское поле); серверный рейтинг и отклонение для разных навыков ещё необходимо реализовать.
4. Возврат в незавершённый бой **после полного перезапуска WebView**; снимки партии на сервере уже доступны, но восстановление UI необходимо доработать.
5. Нужны итоговые UX-правки, настоящий контроль VK/GitHub Pages на двух устройствах, нагрузка, антиспам и лимиты пользователей, финальные локализации и ручная приёмка.
6. В текущем staging используется защищённый HTTP-поллинг примерно 2,4 с, пока без WebSockets. Для 10+0 допустимо в прототипе, до массового запуска оценить WebSocket Durable Objects Hibernation.

## Турнирный Elo и восстановление результатов — staging (03.11.2026)
- **Победа повышает общую Мощь, поражение снижает**; применяется существующая формула Elo **K=32**, зависящая от Мощи обоих игроков. При равной Мощи это +16 / −16; ничья пересчитывается относительно ожидаемого результата.
- Чистая формула вынесена в общий `game/js/power-elo.mjs` и применяется и Путешествием, и Tournament Worker. Никакой параллельной турнирной формулы нет.
- Серверный Durable Object формирует неизменяемую запись результата и индивидуальный Elo receipt только после подтверждённого завершения матча. Клиент не может заявить победу через публичный endpoint.
- Клиент импортирует подтверждённый outcome и применяет его к текущей Мощи через существующий `settlePlayerRating` с уникальным receipt `tournament:<matchId>:<color>`, чтобы повторные опросы и перезагрузка не начисляли очки дважды.
- Турнир при повторном открытии восстанавливает действующий или завершённый матч через подписанную сессию и серверный snapshot. Экран результата показывает изменение Мощи до/после и величину ±.
- `rpchess:power-updated` сохраняет совместимость с общим клиентским рейтингом и автосинхронизацией VK.
- Сервер подписывает повторную сессию с обновлённым текущим Power перед следующей PvP-партией, чтобы Power в матчмейкинге не оставался устаревшим.
- Тесты расширены без новой инфраструктуры: численный паритет Elo, уникальность/стабильность server receipt, двухклиентский матч +16/−16, повторное открытие после перезагрузки без повторного начисления.
- **Ограничение безопасности:** текущее начальное Power для PvP на staging поступает с клиента; гостевые аккаунты и VK без `VK_APP_SECRET` ещё не являются защищённой рейтинговой идентичностью. Поэтому PvP **не готов к production** и **Осколки чести не начисляются**. Перед выпуском требуются проверка VK/гостей, серверный реестр Power и антифарм; текущий Elo — функциональный прототип, не доказательство защищённой экономики.



## Защищённый PvP-рейтинг: этап 1 (03.11.2026)
- Рейтинговая партия возможна **только при случайном подборе двух подтверждённых VK-профилей**. Гостевые игры и приглашения — товарищеские: без прироста/потери Мощи и без Осколков чести.
- Параметры запуска VK проверяются на сервере по HMAC и сроку действия. Старый подписанный серверный токен может использоваться до истечения срока; неподписанный запрос не может задавать ID или Мощь.
- Один SQLite-backed `TournamentAccount` Durable Object на VK-профиль хранит рейтинговую Мощь и неограниченные по числу идентификаторов журнальные записи `tournament:<matchId>:<color>`. Начальная подтверждённая рейтинговая Мощь **500**, независимо от числа, переданного браузером.
- После серверного завершения матча каждому аккаунту один раз применяется Elo K=32; при перезапуске или сетевом сбое незавершённые начисления можно повторить без двойной выплаты.
- Для защиты от простейшего фарма пары допускается не более **двух рейтинговых встреч** между двумя подтверждёнными VK-аккаунтами за скользящие 24 часа. Последующие встречи товарищеские.
- Турнир теперь показывает серверный рейтинг отдельно от общей Мощи. Существующий рейтинг Путешествия/Арены остаётся клиентским: строго подтверждённое сервером PvP-изменение прибавляется или вычитается из общей Мощи один раз, без замены её исходного значения.
- **Открытое продуктовое ограничение**: локальная Мощь (растёт в PvE) и защищённая серверная Мощь (растёт в PvP) могут иметь разные исходные значения. До публичного рейтингового релиза требуется согласовать миграцию и безопасность единой Мощи. Никаких наград Осколками чести пока нет.
- Автоматический разбор ошибок в будущем будет **только в Турнире и Арене**. В Путешествии обучение на ошибках не добавляется.


## Политика общей и соревновательной Мощи (03.11.2026)
- **Общая Мощь** Путешествия/Арены остаётся прежней клиентской прогрессией со всеми действующими боями, заданиями и переносом между забегами. Она не выдается за защищённый соревновательный рейтинг.
- **Серверный рейтинг Турнира** для подтверждённого VK-аккаунта начинается с 500 и изменяется только по результатам подтверждённых сервером рейтинговых PvP-партий. Из клиента нельзя заменить его числом общей Мощи.
- Рейтинговая победа/поражение создаёт ровно один идентифицируемый серверный delta receipt; клиент применяет **только дельту** к общей Мощи, не перезаписывая её исходный показатель. Это сохраняет уже накопленную прогрессию без доверия к ней для рейтингового подбора.
- Гостевые и приглашённые товарищеские партии не меняют ни один рейтинг. Мощь игрока для публичного рейтингового подбора читается из серверного профиля.
- Тесты с реальными пользователями VK, дальнейшая антифарм-защита и выплаты Осколков чести **отложены по решению владельца**. Не считать staging официальным рейтинговым релизом.


## Единая очередь и выбор транспорта — кандидат PR #182 (06.11.2026)

**Только кандидат на release. Нельзя считать работающим в production до приёмки.**

**Фактическая целевая цепочка:** GitHub Pages / VK / Web (HTML5) → выбор API транспорта в браузере → либо прямой HTTPS Cloudflare, либо Yandex API Gateway (HTTP proxy) → один `rpchess-tournament-profile-preview` Worker → `TournamentLobby('world')` Durable Object для общей очереди и приватных комнат; `TournamentMatch` Durable Object на каждую партию, `TournamentAccount` на подтверждённый аккаунт. RPChess Profile отдельно: `rpchess-profile-preview` Worker → D1. Турнир проверяет Profile через доверенную Cloudflare service binding. Яндекс не хранит пользователей, матчи или ходы.

- Клиент Profile и клиент Tournament **выбирают маршруты независимо**: сервис, доступный напрямую, не переходит через Яндекс из-за блокировки другого сервиса.
- Автовыбор безопасно проверяет GET health и маршрут к `/v1/session` с браузерной CORS preflight; запросы GET идут параллельно. Рабочий маршрут фиксируется после выбора, POST/PUT автоматически НЕ перепосылаются в другой транспорт.
- При неясном результате join (например, HTTP 502 после серверного выполнения) клиент сначала проверяет `/v1/queue/status`, а не отправляет повторный `newSearch:true`, который мог бы удалить уже созданный матч.
- Действующая подписанная турнирная сессия переиспользуется: `queue/join` на сервере самостоятельно читает защищённую рейтинговую Мощь из реестра аккаунта; повторные создание сессии и запрос профиля для каждого поиска не нужны.
- Прямая очередь и очередь Яндекса уже подтверждены через **один Worker** на реальной тестовой приватной партии: [GitHub Actions 42259660513](https://github.com/mobigametim-bit/RPChess/actions/runs/42259660513). В начале один игрок шёл через Yandex, другой напрямую через Cloudflare; совпали match ID, доски, ходы и завершение.
- Играбельный кандидат размещается **только в существующем Cloudflare static preview**: `https://rpchess-profile-game-preview.mobigametim.workers.dev/?rpchess_profile=1`. Изменение STATIC файлов не деплоит Worker или D1 и не меняет GitHub Pages.
- Существующий `rpchess-tournament-preview` и v4 Worker имеют **разные** пространства Durable Objects. Уровень данных невозможно объединить простой сменой клиентского URL. Для legacy предусмотрен явный тестовый флаг `?rpchess_tournament_backend=legacy`, но **это не миграция активных матчей**.

**Обязательный безопасный порядок релиза:**
1. Провести ручную проверку кандидата на двух реальных клиентах; сначала приватная партия, потом публичная очередь из РФ и другого региона. Учесть, что сам статический `workers.dev` preview может быть недоступен в РФ.
2. Удостовериться, что на canonical Tournament Worker задеплоен обновлённый набор разрешённых VK Origin; не ослаблять проверку до `*`. Секреты и D1 не менять.
3. Согласовать сохранение незавершённых legacy-матчей и переход клиентов (дренирование старых сессий или отдельный контролируемый cutover). Не сливать, пока не решено.
4. Проверить ошибку/повтор поиска, cancel-vs-late-join, сохранение гостевого/VK профиля, локализацию, проигрыш и рейтинг. Только после подтверждённой пользовательской приёмки — выпускать в `main`, сохраняя оба Worker до завершения перехода.
5. Существующие плавающие HTTP 502 Yandex → Cloudflare не устранены: браузерный health/prefight probe не является лечением сетевого шлюза. Нужен мониторинг канала, а если ошибки сохраняются — устранение на уровне Yandex интеграции/маршрута.

**Тестовая безопасность:** не помещать автоматизированные браузерные тестовые аккаунты в живую публичную очередь — можно случайно сопоставить их настоящим игрокам. Cross-route автоматический тест использует приватную комнату, публичная очередь требует согласованной ручной приёмки.
