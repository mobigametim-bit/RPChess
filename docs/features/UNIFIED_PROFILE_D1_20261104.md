## Безопасный план и текущее состояние

- **Ветка:** `feature/unified-player-profile-20261104`, [черновой PR #173](https://github.com/mobigametim-bit/RPChess/pull/173), основание — ветка GamePush PR #172.
- **Флаг Web/PWA/VK:** `?rpchess_profile=1`. Без него действующая система сохранений работает как раньше.
- **Клиент:** `game/js/profile-client.mjs` создает/resume RPChess ID и автоматом синхронизирует `localPayload()` (Power, Chronicle, Arena, tutorial, ad receipts, новые активные забеги). На Web/PWA сервер возвращает случайный RPChess ID и секретную capability длиной 32 байта; клиент хранит её только локально. Через пустой публичный ID нельзя получить ни статистику, ни изменить профиль.
- **VK:** подписанные `vk_*` параметры launch получает клиент из URL либо VK Bridge `VKWebAppGetLaunchParams`; Worker проверяет HMAC через защищённый `VK_APP_SECRET` и актуальное время `vk_ts`. Сервер привязывает VK ID к **собственному**, а не к GamePush ID. В другой игре/на другой площадке тот же человек получает отдельный RPChess ID. При потере устройства VK профиль восстанавливается по вновь подписанному запуску, Web — только по сохранённому секрету.
- **Первое восстановление старого прогресса VK:** после подтверждённого входа в Worker клиент однократно **читает** старые `rpchess_v1_cloud_*` ключи из VK Cloud через VK Bridge. Только `rating`, `chronicle`, события `arena`; старые `run` и `arena.match` **НЕ** передаются. Worker делает атомарный update с `migrated_vk_v1=1`; повторный импорт не дублирует данные. Оригинальная VK-статистика остаётся резервной копией. Промежуточные GP/VK v2 ключи тоже не удаляются.
- **D1:** используем известную бесплатную `rpchess-leaderboard` D1, но с *новыми* таблицами `rpchess_profile_v1` и `rpchess_profile_token_v1`. `leaderboard_v1` и текущие игроки не изменяются, данные Турнира в Durable Objects не меняются. Отдельный Worker `rpchess-profile-preview` с самостоятельными permissions/endpoints.
- **Загрузка браузера:** `game/index.html` выбирает пространство сохранений по последнему подтверждённому ID, `game/js/platform.mjs` изолирует его как `rpchess.profile.v1.{platform}.{uuid}.*`. При смене VK аккаунта локальные сохранения другого игрока не читаются.
- **Проверка версии:** `PUT /v1/profile` требует текущую `revision`, иначе получает `409 revision_conflict`. Сохранять локально и показывать `conflict`, не перезаписывать другой девайс вслепую. Отсутствие сети не удаляет локальный прогресс.
- **Деплой:** `.github/workflows/profile-preview.yml` сначала `npm run gate:local` и браузерный smoke, затем `CREATE TABLE IF NOT EXISTS` *только новые таблицы* в D1, `wrangler deploy` нового API Worker + отдельной static-игры `rpchess-profile-game-preview`, затем живой тест регистрации гостя и двух браузерных запусков.
- **Секрет VK:** после создания нового Worker владелец добавляет `VK_APP_SECRET` в секреты **только** Worker `rpchess-profile-preview` через Cloudflare; значение не посылать в чат/GitHub. Не путать с публичным GamePush Token. Пока секрет не установлен, VK endpoint сознательно отклоняет неподтверждённые входы.
- **GamePush:** SDK может продолжать показывать ошибку `userId not found` в VK — собственная идентификация RPChess не является исправлением чужой авторизации. Для проверки собственной базы использовать VK dev URL без `rpchess_gamepush=1`, с одним `?rpchess_profile=1`. Затем отдельно исправить SDK интеграцию/проверить рекламу.

## Этапы проверки

1. Автоматические тесты: backend RPChess ID, 256-битный token (в D1 только SHA-256 hash), подпись VK, CAS конфликт, только однократный импорт и исключение старого забега.
2. Web: новый ID, прогресс в D1 и localStorage, reload тот же ID, отдельный браузер — другой ID.
3. PWA: установленное приложение с тем же origin *обычно* может использовать тот же browser storage, но разные установки/очистка данных могут лишить ключа. Отдельный код восстановления пока не делаем.
4. VK dev (только после секрета): Power, Chronicle, Arena, старый VK Cloud не изменён; новый RPChess ID восстанавливается на другом устройстве.
5. Турнир и общие рейтинги: использовать RPChess ID в последующем отдельном изменении — текущий PvP Worker остаётся неизменным, рейтинговые расчёты на основании неподтверждённых клиентских сохранений недопустимы.

## Ограничения и платные сервисы

- Данные одиночного клиента **не защищены от читерства**; запрещено начислять денежные/рейтинг-награды из произвольно отправленного браузером snapshot. Сохранения предназначены для персонального прогресса, рейтинговые игры — только после серверного подтверждения результата.
- Без секретного токена Web/PWA не восстановить после очистки/смены устройства; ключ можно восстановить только если он сохранился. В будущем можно добавить *необязательный* код восстановления.
- Клиент работает офлайн локально; одновременная игра двух устройств, конфликт версий требует явного разрешения и не стирает данные молча.
- Не активировать платный GamePush Backend, Admin GraphQL и Hosting. Учитывать бесплатные лимиты Cloudflare.
- **Никакого merge `main` и переключения VK production/Яндекса** без приёмки владельцем.

Документация Cloudflare D1: https://developers.cloudflare.com/d1/worker-api/ и https://developers.cloudflare.com/d1/reference/migrations/.

## 2026-11-05 — общая Летопись TOP-10 и связка RPChess ID → Турнир

**Продуктовый контракт:** на стяге снова «Великие полководцы», собственное место и **настоящий глобальный TOP-10**; личная история завершённых походов в новом профильном режиме больше не подменяет лидерборд. Порядок рейтинга: Glory DESC, week DESC, Power DESC, время первого результата ASC, канонический owner-key ASC. Формула Glory остаётся `floor(sqrt(week * power) / 10)`.

**Таблицы и сервер:**
- Добавлена только `rpchess_leaderboard_v2` в прежнюю бесплатную D1. Историческая `leaderboard_v1` не изменена: сервер объединяет старые VK и новые RPChess записи через SQLite window functions. Если VK игрок уже получил RPChess ID, обе записи принадлежат одному участнику; выбирается лучший результат. Гости Web/PWA тоже видны в общем TOP-10.
- `POST /v1/leaderboard/refresh` требует действительный профильный bearer, сначала читает настоящий D1 snapshot, пересчитывает лучший результат среди завершённых походов и активного Путешествия, а затем делает неубывающую запись. Клиент не может отправить *другую* оценку непосредственно на этот endpoint.
- `GET /v1/leaderboard` возвращает первые десять и, при валидном bearer, точное место игрока, даже если он за пределами десятки. Внутренние owner keys и токены не отдаются в рейтинге.
- Данные PvE сохранений остаются **клиентскими, не защищёнными от читерства**. Общий TOP-10 пока информационный и не даёт призов/Осколков чести. Для призового/соревновательного рейтинга понадобятся серверные подтверждения.
- При входе в главное меню профильный клиент сначала синхронизирует D1, затем обновляет рейтинг, поэтому свежая Мощь и текущий поход не теряются из-за debounce.

**Турнир:**
- `GET /v1/tournament-binding` на профильном Worker возвращает только аутентифицированному пользователю привязку RPChess ID и провайдера. Турнирный Worker сам проверяет секретный bearer у Profile API (не верит переданному браузером UUID). Неправильный или несовпадающий VK-профиль отвергается.
- Новый **изолированный** `rpchess-tournament-profile-preview` имеет собственные Durable Objects и серверный турнирный Elo; существующий `rpchess-tournament-preview` и рейтинговые матчи не меняются.
- VK профиль, подтверждённый сервером профилей, может играть рейтинг; Web/PWA получают стабильную идентичность в обычных PvP матчах без рейтинговых начислений. Начальный рейтинг подтверждённого игрока берётся из серверного ledger (500), а не из клиентской Мощи. Осколки чести за PvP по-прежнему не выдаются.
- В режиме RPChess ID игровой клиент отправляет токен только изолированному Tournament Worker по HTTPS. В обычной версии прежний Tournament endpoint и старая авторизация не изменены.

**Тесты:** расширенные `tests/profile-worker.cjs` проверяют SQLite-ранжирование, объединение legacy-VK и нового VK ID, неизменность рекордной Glory, а также выдачу Tournament binding. `tests/tournament-profile-link-local.mjs` проверяет поддельный UUID, неверный bearer, несовпадающие VK и стабильность Web/VK личности. Profile staging workflow проводит локальный тест, деплой отдельного PvP Worker, реальный двухгостевой PvP smoke и обмен с Profile API.
