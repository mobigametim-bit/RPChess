**Формат:** художественные тексты на русском для модального окна результата события.  
**Статус:** все **500/500 событий, 2114/2114 решений и 3388/3388 основных исходов** индивидуально переписаны; дополнительно вычитаны **376/376 fallback-исходов**. **Литературная приёмка владельцем игры и ручной playtest ещё не проведены.** Runtime-интеграция и EN-локализация также остаются отдельными этапами.

## 1. Задача

После выбора в событии оставить существующий UI: «Успех» или «Неудача», шанс/бросок, фактические изменения золота/припасов, последствия для персонажей, кнопку продолжения/перехода в бой. Между статусом и фактическими notes добавить **1–2 художественных предложения**, объясняющих, чем закончилось именно выбранное действие.

Не изменять шансы, стоимость, набор эффектов, выбранных героев, RNG, набор событий, структуру маршрутов и экономику. Никаких новых LLM-вызовов в runtime.

## 4. Контракт данных

В JSON на каждое событие идёт объект с полями id, title, race, tone, actors, story, choices.

Для каждого choices[]:
- id, action, chance, role;
- cost, successCost, successEffects, failureEffects, alwaysEffects, kingRisk, warnings — метаданные проверки, **не источник игровых эффектов**;
- success — строка успеха;
- failure — строка неудачи или null, если chance === 100;
- variants.success/failure.recruitUnavailable — запасной текст, если реальный эффект recruit конвертирован в золото;
- variants.success/failure.noEligibleTarget — запасной текст, если wound/death не нашёл допустимую цель.

Переменные внутри текстов:
- **{{heroName}}** — реальный исполнитель: исходный role-gated герой или явно требуемый именной герой;
- **{{affectedHeroName}}** — персонаж, который *фактически* пострадал по применённому эффекту.

Обе подстановки должны быть безопасными и не должны требовать склонения русского имени.

## 5. Как встроить без регрессии

### 5.1. Источники runtime

В текущей базе:
- game/js/events-core.mjs: normalizedEvent(...), resolveEventChoice(...), applyEffect(...).
- game/js/events-app.mjs: renderEvent(...), renderOutcome(event).
- game/js/events/event-hero-choices-v5.mjs: исходные sourceChoiceId и персональные варианты.

После выбора уже есть persist state.currentEvent и state.currentEvent.outcome:
- state.eventId;
- outcome.choiceId;
- outcome.success;
- outcome.heroId;
- outcome.notes;
- outcome.combat;
- outcome.roll / chance.

**Не вычислять успех заново.** Текст выбирается по сохранённому outcome.success.

### 5.2. Выбор narrative key

1. Найти событие по state.eventId.
2. Найти уже нормализованное решение по outcome.choiceId.
3. Если это персональный вариант v5, использовать **choice.sourceChoiceId** как ключ текста; иначе outcome.choiceId.
4. Найти строку в JSON: success или failure по фактическому outcome.success.
5. Определить реального исполнителя по outcome.heroId и roster/choice.requiredHeroId; подставить {{heroName}}.
6. Для wound/death использовать **реально применённый** targetId/name; подставить {{affectedHeroName}}. Если никто не пострадал — соответствующий fallback.
7. Для recruit, превратившегося в +18 Gold, использовать recruitUnavailable, а не утверждать, что присоединился герой.
8. Вставить художественный текст *над* существующими outcome.notes, не заменяя notes.

В идеале минимально расширить результат applyEffect(...), чтобы вместе с notes возвращался структурированный receipt (тип эффекта, фактическая delta, targetId и recruitId/fallback). Сохранить receipt в outcome. **Не** парсить локализованную строку notes и не повторять случайный выбор персонажа для получения имени.

### 5.3. Важные краевые случаи

- Вычеты cost применяются до исхода **даже при провале**; narrations не должны утверждать, что деньги вернули.
- Когда Gold/Supplies уже в нуле, реальные delta могут быть обрезаны; цифры брать только из существующих фактических notes.
- Смерть Короля заканчивает забег, а не запускает дополнительный экран.
- wound/death случайного героя никогда не должны переадресовываться Королю.
- roleHero / heroId и именная v5-вариация могут менять фактическую цель эффекта; всегда доверять runtime, а не базовому JSON.
- Стычка/Битва из события **только начинается**; не описывать заранее победу игрока.
- Гарантированный chance 100 не должен отображать несуществующую ветку failure.
- Resolved state после перезагрузки обязан показывать ту же строку, того же героя, те же notes и тот же бой.
- При отсутствии текста/подстановки не показывать пользователю {{...}}. Безопасный fallback — только существующие success/failure + notes.
- Локализация RU/EN: данный пакет содержит **только русскую прозу**. Перед production-приёмкой либо подготовить английские художественные версии и проверить переключение языка, либо явно утвердить продуктовый fallback; недопустимо непреднамеренно смешивать языки.

### 5.4. Размер данных

Документационные JSON содержат избыточные story, action, mechanics и метаданные. **Не** импортировать их целиком в игровую сборку: создать компактный runtime-манифест вида key → {success, failure, variants}, избегая дублирования существующего каталога. По возможности разбить по уже используемым модулям / lazy-load, проверить размер сборки и кеширование.

## 6. Минимально достаточная проверка

Предпочесть расширить существующие tests/events.cjs и tests/events-v5.cjs несколькими осмысленными проверками вместо создания массивных новых тестовых пакетов:
1. Каждый актуальный base-choice ID имеет success; каждый chance<100 имеет failure; chance=100 — без failure.
2. 537 именных вариантов ссылаются на существующие sourceChoiceId и корректно отображают имена.
3. Детерминизм после сохранения/перезагрузки, включая ранение случайного героя и recruit fallback.
4. Не меняются resource deltas, шанс, RNG, наборы фигур, запуск боёв и состояние забега.
5. В случае отсутствия применённой wound/death цели не выводится ложная строка о ранении/гибели.
6. На mobile modal читабелен; художественный текст не вытесняет кнопку продолжения и список ресурсов.
7. На английской локали нет непреднамеренной смеси интерфейсных языков.

6. Минимально расширить существующие регрессионные проверки.
7. Подготовить играбельный preview, **не сливать в main**.
8. Владелец вручную проверяет минимум 10–15 событий разных типов и отдельно принимает тексты/стиль; после правок синхронизировать GitHub docs и Notion согласно принятому процессу проекта.

## 8. Редакторский контроль перед production

Не просто прогнать JSON по тестам: прочитать и отредактировать текстовые исходы, которые звучат шаблонно, неуместно для тона события, повторяются, делают неподтверждённые сюжетные предположения или не учитывают реальную цену. Эталон — E131: конкретное действие, осязаемый итог и уместная короткая реплика. Никакой «дождь, озон, неон» и других повторяющихся атмосферных штампов. Юмор — только там, где он соответствует событию.

**Итог:** **500/500 событий и 376/376 дополнительных fallback-текстов литературно переписаны**. Пакет пригоден для создания *preview-интеграции*, но ещё **не встроен в игровой runtime**, не локализован на английский и не принят владельцем. Перед production обязательны тесты и ручная приёмка.
