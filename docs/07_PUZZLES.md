# 07 — Puzzles

## Статус

Puzzles находится на стадии **UX/spec discussion**. Базовый UX v1 уже согласован; до implementation остаётся утвердить конкретную визуальную шкалу сложности и базовые суммы Gold по уровням.

## Поддерживаемые типы v1

- мат в 1;
- мат в 2;
- мат в 3;
- выигрыш конкретной фигуры / материала.

Для material puzzles цель формулируется **явно по конкретной фигуре**, например:
- `ВЫИГРАЙТЕ ФЕРЗЯ`;
- `ВЫИГРАЙТЕ ЛАДЬЮ`;
- `ВЫИГРАЙТЕ СЛОНА`;
- `ВЫИГРАЙТЕ КОНЯ`.

Игрок не должен угадывать, какой из нескольких материально выгодных вариантов считается авторским решением. В curated library v1 допускаются только задачи, где целевая фигура и оптимальная forced line однозначно валидируются импортёром/движком.

## Источник контента

Основной production-source — **Lichess Open Database: Puzzles**, распространяемая как CC0/public-domain dataset.

Книги Сергея Иващенко не используются как источник production puzzle library.

Исходная многомиллионная база не поставляется целиком с игрой. Developer importer выбирает и валидирует curated offline subset, после чего в RPChess коммитится только нормализованный набор задач.

## Curated набор v1

Ориентир для первой библиотеки — около **2000 задач**:
- 500 × мат в 1;
- 500 × мат в 2;
- 300 × мат в 3;
- 700 × выигрыш конкретной фигуры / материала.

Финальный объём можно скорректировать после проверки размера JSON, качества выборки и распределения сложности.

## Формат данных

Минимальный нормализованный формат:

`id`, `sourceId`, `fen`, `side`, `solution`, `type`, `rating`, `difficulty`, `themes`, `targetPiece`, `materialGain`, `reward`.

`targetPiece` обязателен для material puzzle и хранит конкретную целевую фигуру (`queen`, `rook`, `bishop`, `knight`). Для mate puzzles поле отсутствует/null.

## Import pipeline

Lichess puzzle FEN хранит позицию **до** последнего ошибочного хода исходной партии. Importer должен:
1. загрузить исходный FEN;
2. применить первый UCI-ход из source solution;
3. сохранить получившуюся позицию как фактический puzzle start;
4. сохранить оставшуюся forced line как решение задачи;
5. валидировать позицию и решение шахматным движком;
6. для material puzzles определить конкретную обязательную целевую фигуру и отбрасывать неоднозначные позиции.

Puzzle runtime не обращается к Lichess во время игры и работает полностью offline.

## Travel integration — APPROVED

Puzzle становится **пятым playable типом Travel Choice**:

`Skirmish / Battle / Settlement / Event / Puzzle`.

Каждая из трёх Travel-карточек независимо выбирает один из пяти типов, поэтому долгосрочная доля каждого типа близка к **20%**; дубликаты типа внутри одной тройки допустимы.

Выбор Puzzle-карточки является обычным committed Travel transition и расходует стандартный **1 Supply**. Дополнительной платы внутри Puzzle нет.

## UX задачи — APPROVED

Puzzle использует обычную шахматную доску RPChess, но не является полноценной партией.

Перед началом игрок видит короткую конкретную цель:
- `МАТ В 1` / `МАТ В 2` / `МАТ В 3`;
- либо `ВЫИГРАЙТЕ ФЕРЗЯ / ЛАДЬЮ / СЛОНА / КОНЯ`.

Игрок делает ходы непосредственно на доске. После правильного хода ответ соперника из forced solution выполняется автоматически, затем управление возвращается игроку до завершения решения.

Puzzle воспроизводит исходную FEN-позицию стандартными белыми/чёрными фигурами. Персонализированный roster не подменяет фигуры задачи, чтобы не менять смысл позиции.

## Ошибки и попытки — APPROVED

Игрок получает **3 попытки**.

Неправильный ход не продолжает ложную ветку: он мгновенно откатывается, позиция возвращается к корректному состоянию решения, а счётчик ошибок увеличивается.

После третьей ошибки Puzzle считается проваленным.

## Gold reward — APPROVED FRAMEWORK

Базовая награда Puzzles v1 — **Gold**.

Множитель зависит от числа ошибок:
- 0 ошибок → **100%** базовой награды;
- 1 ошибка → **70%**;
- 2 ошибки → **40%**;
- 3-я ошибка → Puzzle провален, **0 Gold**.

Сама базовая сумма Gold зависит от уровня сложности Puzzle. Конкретные суммы по уровням ещё должны быть утверждены.

## Сложность по неделям — APPROVED RULE

На текущем этапе сложность Puzzle зависит **только от номера недели забега**. В дальнейшем эта модель может быть заменена более адаптивной системой.

Каждые **8 недель** происходит повышение уровня сложности.

Предлагаемое визуальное обозначение — переиспользовать общую шкалу RPChess **★1…★12**, уже знакомую по Skirmish/Battle:
- недели 1–8 → ★1;
- 9–16 → ★2;
- 17–24 → ★3;
- 25–32 → ★4;
- 33–40 → ★5;
- 41–48 → ★6;
- 49–56 → ★7;
- 57–64 → ★8;
- 65–72 → ★9;
- 73–80 → ★10;
- 81–88 → ★11;
- с 89-й недели → ★12, далее cap.

На Travel-карточке может использоваться компактная форма `ЗАДАЧА · ★5`; внутри Puzzle — `МАТ В 2 · СЛОЖНОСТЬ ★★★★★`. Сырой Lichess puzzle rating игроку не показывается; он используется только importer/runtime для формирования соответствующего difficulty pool.

Визуальная шкала ★1…★12 пока считается **предложением**, а не окончательно утверждённым UI-решением.

## Подсказки

**Hint-механика не входит в текущий Puzzles v1 spec.** Для неё будет отдельное обсуждение и отдельная механика; не добавлять стандартную кнопку, автоматическую подсказку или штраф за подсказку без отдельного решения пользователя.

## Архитектурное правило

Puzzle engine не зависит от конкретного источника контента. Позиции импортируются пакетами в универсальный data-format и валидируются chess rules/Stockfish. Source-specific особенности Lichess изолированы внутри developer importer.

## Остаётся утвердить до implementation

- визуальное обозначение сложности: предложена общая шкала ★1…★12;
- конкретное распределение Lichess rating/type mix внутри каждого ★-уровня;
- базовые суммы Gold для ★1…★12.
